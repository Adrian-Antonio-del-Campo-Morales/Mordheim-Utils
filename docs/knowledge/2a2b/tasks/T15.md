# T15 — Revisión final, gates y commits locales

## Objetivo e inicio
Cerrar la integración mediante revisión del cambio completo, validación vigente y commits locales trazables. Leer [contrato de coordinación](../README.md). Dependencias: T13 y T14 cerrados. La publicación actual de estos documentos es distinta: la futura ejecución de T15 termina localmente, sin push ni despliegue. Base de planificación 9118ca2; usar el HEAD real y la evidencia actual al ejecutar.

## Propiedad y límites
Propiedad del coordinador/integrador: revisión final, orden de commits y estado del índice principal. Otros agentes entregan evidencia, no actualizan el principal. Mantener staging y herramientas útiles. No incluir cambios ajenos ni limpiar worktrees para obtener estado limpio. No hacer push, PR remoto ni publicación.

## Pasos
- [ ] Confirmar T01–T14 cerradas y que la revisión validada coincide con el contenido actual. Verificar reservas de archivos y terminar escritores concurrentes antes del gate final.
- [ ] Revisar diff completo por subsistema: datos, contratos, motores, interfaz y pruebas. Comprobar conservación de staging y de datos anteriores.
- [ ] Exigir resolución de toda obligación de automatización acordada: no cerrar por estar el YAML publicado ni convertir pendientes en manuales para aprobar.
- [ ] Revisar evidencia T13/T14, sus limitaciones y cualquier cambio posterior; reabrir tarea si la corrección invalida su aceptación.
- [ ] Ejecutar gate integral existente sobre la revisión final. Complementarlo con evidencia semántica/de motores T14: run-ci no sustituye todas las pruebas de motores.
- [ ] Revisar archivos generados y diferencias finales; registrar exclusiones justificadas. No forzar outputs ignorados en Git.
- [ ] Preparar commits locales coherentes por capas/dependencias cuando el diff lo permita; cada commit debe incluir pruebas/contratos necesarios. Seleccionar rutas o bloques propios, nunca git add indiscriminado.
- [ ] Verificar commits creados, estado final y divergencia con la referencia remota local conocida. No afirmar sincronización remota sin actualización de referencias.
- [ ] Actualizar documentación/evidencia de cierre mediante coordinador y entregar hashes, gates, limitaciones y confirmación de ausencia de push.

## Comandos existentes
Desde raíz, adaptando únicamente las rutas seleccionadas para staging Git:
```powershell
python tools/mordheim-utils.py run-ci
git -c "safe.directory=D:/DEVEL/Mordheim/Mordheim-Utils REPO-REWORK" diff --check
git -c "safe.directory=D:/DEVEL/Mordheim/Mordheim-Utils REPO-REWORK" status --short --branch
git -c "safe.directory=D:/DEVEL/Mordheim/Mordheim-Utils REPO-REWORK" diff --stat
git -c "safe.directory=D:/DEVEL/Mordheim/Mordheim-Utils REPO-REWORK" log -8 --oneline
git -c "safe.directory=D:/DEVEL/Mordheim/Mordheim-Utils REPO-REWORK" rev-list --left-right --count '@{upstream}...HEAD'
```
Si no hay upstream, declararlo. Registrar las órdenes reales de add/commit y sus hashes; este documento no autoriza incorporar cambios ajenos. No usar reset/clean para retirar trabajo concurrente.

## Fin y evidencia
- [ ] Gate final aprobado, revisiones funcionales y de datos vigentes, todas las tareas cerradas.
- [ ] Staging conservado; cambios propios confirmados en commits locales; trabajo ajeno preservado.
- [ ] Hashes, estado, divergencia y resultados comunicados; ningún push/despliegue efectuado durante la ejecución.
Una validación bloqueada se registra como pendiente y no permite anunciar integración completada.
