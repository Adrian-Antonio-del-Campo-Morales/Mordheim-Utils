### 2. Interfaz final

La operación de promoción es explícita y tiene dos puertas: previsualizar no es escribir.

```powershell
# Normalización del staging (sin cambios de contrato):
python tools/ingestion/normalize_staging_for_promotion.py --check [--json] [--passes market,items]
python tools/ingestion/normalize_staging_for_promotion.py --write

# Promoción: previsualización completa, sin escribir nada.
python tools/ingestion/normalize_staging_for_promotion.py --promote [--json]

# Promoción: escritura explícita, SIEMPRE con destino nombrado.
python tools/ingestion/normalize_staging_for_promotion.py --promote --write --destination build/tmp-promotion
```

- `--promote` sin `--write` es un **preview**: imprime el destino, el recuento por familia,
  una línea por registro (`new`, `merge`, `variant`, `redirect`, `exclude`, `conflict`,
  `already-promoted`) y los documentos que escribiría. Exit **0** si no hay conflictos, **2** si
  los hay (con el detalle en `stderr`).
- `--promote --write` **exige** `--destination`: sin él devuelve exit 2 y no escribe nada. La KB
  activa nunca se escribe de forma implícita.
- El destino es un root que refleja `sources/knowledge`. La primera pasada lee la KB como base de
  cada documento que fusiona (un destino temporal está vacío); la segunda lee lo que escribió la
  primera, que es lo que la vuelve vacía. Un destino temporal queda así como «la KB después de la
  promoción» **solo para los documentos que la promoción toca**.
- Tras escribir, la CLI pasa los YAML por `tools/knowledge/maintenance/format_yaml.py` (el
  formateador canónico ya usado por la normalización) y cada documento se valida contra el
  esquema de su familia KB **antes** de escribirse.
- API reutilizable: `staging_promotion.promote(root=None, trees=("2A","2B")) -> Promotion` con
  `.actions`, `.counts()`, `.families()`, `.as_dict()`, `.summarise()`, `.conflicts`, `.write()`
  (que lanza `PromotionRefused` con la lista de colisiones).

### 6. Evidencia de no mutación e idempotencia

- **No mutación del preview**: `test_a_preview_writes_nothing` calcula el `sha256` de cada YAML
  de `sources/2A`, `sources/2B` y `sources/knowledge` antes y después de `promote()`; idénticos.

1. **El destino es una superposición, no una KB completa**: solo se escriben los documentos que la

   `ITEM_REDIRECTS` como tabla de referencia. Tampoco se promociona `registry/bindings.yaml` ni
   `missing-item-stubs.yaml`.
3. **`ITEM_FILES` (kind → documento KB) es una decisión declarada de esta tarea**: `miscellaneous.yaml`
   es el cajón heredado de la KB y nunca recibe un registro nuevo (solo fusiones, como
   `horsemans_hammer`). Un reparto distinto es una decisión editorial, no un cambio de herramienta.
4. **Validación de forma, no semántica**: cada documento se valida contra el esquema de su familia
   KB antes de escribirse, pero **no** se carga el resultado con `mordheim_knowledge.loader`
   (referencias, bindings y construcción). Eso pertenece a T07/T13.
5. **No se reescribe ningún id de la KB**: los 26 ids fuera de convención siguen como están.
6. **Cobertura del cotejo**: el preview decide sobre las 144 altas y los 41 registros de identidad
   del mapa, pero **no** vuelve a comprobar equivalencia semántica de los 144 ítems nuevos
   (barrido de identidad de T04 §8.7). No se repitieron T02, T03 ni T04.
