# T13 — Reglas del Combat Simulator

## Inicio y coordinación

- Abre la fase 3 después del commit local de T12.
- Usa exclusivamente las obligaciones `Combat Simulator` clasificadas por T06.
- Fijar primero el mecanismo modular y sus contratos. Solo después pueden repartirse backends con archivos disjuntos.
- Propiedad candidata: motor modular, vectorizado, nativo, especificaciones semánticas y pruebas de combate asignadas. La KB no se edita automáticamente.

## Objetivo

Automatizar los efectos de combate 2A/2B dentro de los mecanismos actuales y mantener equivalencia entre backends aplicables. No crear sistemas nuevos de despliegue, ocultación, disparo o resolución de magia de batalla; sus reglas conservan texto y exclusión concreta.

## Pasos

- [ ] Extraer de T06 los IDs, fases, condiciones, destinatarios, duración, decisiones y consumo RNG de combate.
- [ ] Trazar cada operador real y todos sus llamadores, incluidos compilación y pools.
- [ ] Definir primero casos deterministas con dados y decisiones explícitos en las especificaciones existentes.
- [ ] Implementar el mecanismo modular mínimo reutilizando operaciones actuales.
- [ ] Llevar el mismo comportamiento al vectorizado y nativo cuando soporten ese flujo.
- [ ] Mantener orden lógico de RNG, decisiones, fases, consumo/expiración y estado observable.
- [ ] Probar activación, ausencia, empate, consumo/expiración y una composición relevante por mecanismo.
- [ ] Probar mutaciones negativas solo mediante fixtures o procesos aislados.
- [ ] Recompilar el backend nativo mediante su procedimiento existente cuando cambie; no editar C/C++ generado.
- [ ] Registrar si las pruebas usaron extensión recompilada o fallback; un backend no disponible queda pendiente.
- [ ] Actualizar marcas/evidencia de implementación solo después de probar el comportamiento real y con propiedad asignada.
- [ ] Entregar efectos cubiertos, backends, semillas/vectores y límites a T14.

## Fin y evidencia

Cada obligación de combate incluida tiene prueba determinista sobre el motor real y comportamiento equivalente en todos los backends aplicables. Ningún fallback, comparación estadística o marca `implemented` sustituye esa evidencia.
